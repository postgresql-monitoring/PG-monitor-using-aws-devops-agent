Automating Amazon RDS for PostgreSQL investigations with AWS DevOps Agent, MCP, and Agent Skills

AWS DevOps Agent investigates operational events and delivers findings to your team. In this post, we walk through an architecture that exposes PostgreSQL diagnostic tools to AWS DevOps Agent as Model Context Protocol (MCP) tools. The tools run in an AWS Lambda function, and Amazon Bedrock AgentCore Gateway hosts the MCP endpoint. An AWS DevOps Agent skill defines the investigation steps, severity thresholds, and report format. The proposed two-stack design would provision the infrastructure; the published repository does not yet include these templates. We then follow two illustrative investigations and one observed test that combine built-in Amazon CloudWatch telemetry with direct PostgreSQL access through the Gateway.

Solution overview

This solution uses AWS DevOps Agent, Amazon Bedrock AgentCore Gateway, and AWS Lambda to automate database investigations for Amazon RDS for PostgreSQL. The following diagram shows the architecture.

The solution has three main components.

AgentCore Gateway

AgentCore Gateway is a fully managed MCP endpoint between AWS DevOps Agent and the database tools. You register the Lambda function as a target and define its tool schemas. The Gateway turns MCP tool calls into Lambda invocations, so you do not run an MCP server. An MCP client connects to the Gateway URL over Streamable HTTP and authenticates with Signature Version 4 (SigV4). It discovers and calls tools with the standard tools/list and tools/call requests.

In this solution, the Gateway provides:

  • SigV4 authentication for every caller.
  • An allowlist, so the agent can call only the registered tools.
  • Database credentials that stay in AWS Secrets Manager. The agent never sees them.
  • One endpoint for AWS DevOps Agent and any other MCP client that can sign the request.

AWS DevOps Agent

AWS DevOps Agent is a managed service that investigates incidents. You connect it to your AWS account and to the tools behind the Gateway. The agent receives alarms, decides what to check, calls the tools it needs, and sends findings to your team. It reads AWS data through a read-only IAM role. It gets database detail only through the Gateway. The agent has no database connectivity and no access to database credentials.

AWS DevOps Agent Skills

A skill is a directory of Markdown instructions. The postgres-investigation skill in this post is organized as:

postgres-investigation/
├── SKILL.md
└── references/
    └── tool-reference.md

SKILL.md is the only required file. The frontmatter names the skill and says when to use it. The body holds a five-step method. The description is the trigger. When an incoming request matches the wording, the agent loads the skill.

The five steps:

  1. Triage. Read health from Amazon CloudWatch and CloudWatch Database Insights. Set severity against fixed thresholds for CPU, connections, read latency, and freeable memory.
  2. Diagnose. Find the dominant wait from get_activity_summary and get_wait_events.
  3. Drill down. Lock contention, CPU, I/O, connection pressure, or replica lag. Each path calls only the tools that fit it.
  4. Correlate. Decide whether the problem is a spike or a standing condition by comparing the incident window with the hour before it.
  5. Recommend. Report severity, root cause, evidence, and fixes in priority order. State that no session was terminated.

Every step reads built-in AWS telemetry first and uses the query tools only for the session, lock, and statement detail that telemetry does not expose. references/tool-reference.md holds the thresholds and each tool's arguments.

To adapt the skill, edit SKILL.md and its references, rebuild the package, and upload or publish the updated skill in the Agent Space. Confirm the new version is enabled before starting another investigation. The skill is managed separately from the infrastructure stacks.

How an investigation flows

  1. A CloudWatch alarm invokes a webhook Lambda, which posts an HMAC-signed event to the Agent Space webhook. You can also start an investigation from the Agent Space chat. Before a full investigation, the agent compares the event with active investigations and either links it or starts a new one.
  2. The agent loads postgres-investigation, which sets the steps, the thresholds, and the report format.
  3. Through its IAM role, the agent reads CloudWatch metrics, Database Insights, and CloudWatch Logs to see which metric is high and which wait dominates.
  4. For blocking chains, expensive statements, or missing indexes, the agent calls the MCP tools through the Gateway. The Gateway authenticates with SigV4. The query Lambda, in a private subnet, reads the database secret from Secrets Manager and returns session and statement detail. The agent never sees the password.
  5. The agent sends severity, root cause, and recommended fixes to the Agent Space. You can also fan out to Slack, email, or the channel your space is connected to.

Built-in telemetry is the monitoring layer. It shows what kind of problem you have. The MCP tools are the investigation layer. They show which backend, which statement, and which lock.

PostgreSQL tools

RDS for PostgreSQL has no SQL Server-style Query Store or shared execution-plan history accessible through ordinary monitoring views. The pg_stat_statements extension provides cumulative, normalized statement execution statistics, not a chronological query log. A time-window comparison requires timestamped snapshots or historical telemetry. The query Lambda source implements eleven fixed monitoring tools; EXPLAIN remains disabled.

Tool What it does
check_extensions Checks that pg_stat_statements is installed
get_activity_summary Counts sessions by state and wait type
get_blocking_sessions Shows blocking chains and the head blocker
get_slow_queries Lists statements running longer than a threshold
get_top_statements Lists top statements by total time, mean time, calls, or reads
get_wait_events Shows current wait events
get_lock_summary Counts locks by type, mode, and granted
get_index_usage Compares sequential scans with index scans
get_unused_indexes Lists nonunique indexes with no recorded scans in the current statistics window; this alone does not justify dropping an index
get_database_stats Returns commits, rollbacks, deadlocks, and block hits
get_replication_lag Reports physical standby or read-replica replication indicators where available; lag values can be null and are not always a measure of current backlog
explain_query Runs EXPLAIN for one SELECT identified by queryid

explain_query is optional. It generates an estimated plan rather than recovering another session's historical plan. Use plain EXPLAIN, not EXPLAIN ANALYZE. The diagnostic role requires appropriate privileges on referenced relations; pg_monitor alone does not provide those privileges. Disable the tool when they are not explicitly authorized. A statement prefix check is not a complete SQL safety boundary. Require validated single-statement input, narrowly scoped privileges, and read-only transactions; retain the eight-second statement timeout and 50-row response limit. Normalized statements containing placeholders may require additional context and cannot always be explained as stored.

In DevOps Agent, tool names take the form <target>___<tool> (three underscores). The Gateway does not put that name in the JSON body. It sets the Lambda client context field bedrockAgentCoreToolName. The handler has to read it:

name = ""
client = getattr(context, "client_context", None)
custom = getattr(client, "custom", None) if client else None
if isinstance(custom, dict):
    name = custom.get("bedrockAgentCoreToolName", "")
if "___" in name:
    name = name.split("___", 1)[1]

A handler that only reads event["tool"] returns "unknown tool" for every Gateway call. The agent then reports that the diagnostic tools are down, even though a direct invoke of the same function works. Keep the event-body path for tests.

Getting started

Database

The default PostgreSQL parameter group cannot be edited. Create a group in the same family and set:

  • shared_preload_libraries = pg_stat_statements
  • pg_stat_statements.track = top
  • pg_stat_statements.max = 5000
  • log_lock_waits = on
  • log_min_duration_statement = 1000

shared_preload_libraries applies on reboot. Attach the group, wait until the instance is available, then reboot. Connect to the application database and run CREATE EXTENSION IF NOT EXISTS pg_stat_statements.

Create a dedicated non-master login. Grant pg_monitor for monitoring and restrict connectivity to the intended database, reviewing inherited grants and default PUBLIC permissions. pg_monitor is a cluster-level predefined role, not a database-specific grant, and exposes privileged monitoring information. Do not grant application write, schema ownership, or backend-signaling privileges. Verify effective grants before deployment. The skill recommends remediation; it does not execute it.

Store the password in Secrets Manager as JSON: username, password, host, port, dbname.

Network

The query Lambda runs in the database VPC so it can open port 5432. Private subnets often have no NAT gateway. Without a path to Secrets Manager, the function times out before it reaches PostgreSQL.

Use either a NAT gateway on the subnet route table, or an interface VPC endpoint for Secrets Manager. With the endpoint, leave private DNS off if the rest of the VPC should keep resolving Secrets Manager the usual way. Pass the endpoint DNS name to the Lambda and use it as endpoint_url. The endpoint security group accepts TCP 443 only from the Lambda security group. The database security group accepts TCP 5432 only from that same group.

Package psycopg as a manylinux wheel for the architecture you deploy. A wheel built on a developer laptop will not load in Lambda. This stack uses Python 3.12 on arm64.

Stack

In the proposed design, one CloudFormation stack would create the query Lambda, its security group, the Secrets Manager endpoint, and three alarms: CPU utilization, database connections, and read latency. A second stack would create the Gateway, the tool target, the Agent Space, the account association, and the webhook Lambda. The intended alarm integration invokes the webhook function; automatic delivery remains unverified.

Once the missing templates are implemented and validated, the intended deployment uses aws cloudformation package and aws cloudformation deploy. The resource types AWS::BedrockAgentCore::Gateway and AWS::DevOpsAgent::AgentSpace have to be available in the region. Confirm that in the console before you deploy. The CLI version that can package a template is not always the CLI version that has aws devops-agent.

After deploy:

Confirm that the MCP server is registered and associated with the Agent Space using SigV4 and an IAM role authorized for that Gateway. Verify tool discovery and a benign monitoring call before enabling alarm-driven investigations. Direct CloudWatch alarm invocation also requires a scoped Lambda resource policy.

  1. Upload the skill. The repository packaging script generates postgres-investigation.zip, which contains SKILL.md and references/tool-reference.md. In the Agent Space console, add that zip as a skill. With a current AWS CLI:
aws devops-agent create-asset \
  --agent-space-id "$AGENT_SPACE_ID" \
  --asset-type skill \
  --metadata '{"agent_types":["GENERIC"]}' \
  --content "{\"zip\":{\"zipFile\":\"$(base64 < postgres-investigation.zip | tr -d '\n')\"}}" \
  --region "$AWS_REGION"

Rebuild the zip after any edit to SKILL.md. Redeploying the stack does not publish the skill. Verify the CLI asset schema and binary encoding against the installed CLI version; the console upload is an alternative.

  1. In the Agent Space, add a webhook. Store the URL and signing secret securely in the intended Secrets Manager secret. Verify event delivery using a controlled non-production test.

Use case 1: Answer an on-call question from chat

An on-call engineer opens the Agent Space chat and asks whether the PostgreSQL instance is healthy, and whether any alarm has fired in the last hour.

The agent answers from live telemetry first. It reports CPU, freeable memory, connection count against the alarm threshold, and average active sessions. If the instance is small and idle, that answer is enough. If connections or lock waits are elevated, it calls get_activity_summary and get_wait_events through the Gateway and says which wait dominates.

The engineer gets one reply instead of opening Database Insights and a SQL client side by side. The reply names the metric and the threshold. It does not guess a root cause the tools did not return.

Use case 2: Investigate a blocking incident triggered by an alarm

A session starts a transaction, updates one row, and sleeps. Other sessions update the same row and block. The connection count crosses the alarm threshold. The alarm invokes the webhook Lambda, which starts an investigation. Nobody asks a question.

The agent follows the five steps.

  1. Triage. The connection alarm is in ALARM. CPU may be high or quiet. Severity follows the thresholds in the skill.
  2. Diagnose. Lock is the dominant wait, so the skill sends the agent to the blocking path.
  3. Drill down. get_blocking_sessions returns the blocking relationships, PID and transaction age; the reviewed source does not return raw SQL or client identities. get_lock_summary shows the granted lock and the waiters behind it.
  4. Correlate. The agent compares the spike with the prior hour. A single five-minute transaction looks different from a pattern that repeats. If it cannot see the client that opened the transaction, it says so instead of inventing a source.
  5. Recommend. The agent reports the observed blocking relationships and recommends shortening the transaction. It does not recommend pg_terminate_backend, a failover, or a reboot. The login it used cannot run those commands.

The intended result is an investigation that identifies the blocking backend and the associated statement. A current activity snapshot is not proof of the original lock-acquiring statement; report that distinction where evidence is incomplete.

Security considerations

The solution limits database access at three layers.

  • Agent Space role. Read-only AWS API access. No Secrets Manager permission. The agent reaches PostgreSQL only through the registered MCP server, and only the tools on its allowlist.
  • Query Lambda role. Read access to the one database secret. The function retrieves the credentials, so they never reach the agent.
  • PostgreSQL role. Dedicated non-owner monitoring login with reviewed effective permissions and restricted connectivity. Read-only transaction settings supplement, but do not replace, privilege enforcement.
  • Data protection. Redact sensitive statement text, identifiers and literals before returning diagnostic results; treat database-returned text as untrusted data, not agent instructions. Limit the scope and retention of logs.
  • Transport and load. Verify the RDS server certificate over TLS; bound concurrency, query duration, and response size to avoid adding load during an incident.
  • Authorization and audit. Restrict Gateway use and target invocation to intended roles, review secret access, and record diagnostic calls with request identifiers and outcomes without logging secrets or sensitive SQL.

Clean up

Delete the uploaded skill first. It is not part of either stack. Then delete the agent stack and the tools stack. Deleting them removes the Agent Space, the Gateway, the target, the Lambda functions, the interface endpoint, the security group rules added for it, and the alarms. The parameter group, the database, the login role, and the secret remain until you delete those yourself.

Conclusion

CloudWatch and Database Insights provide operational context. MCP tools behind AgentCore Gateway supplement that context with live blocking chains, cumulative statement statistics, lock modes, and index usage. The skill guides the agent to consult built-in telemetry first and query the database when the symptoms justify it. Database privileges and application controls enforce the diagnostic boundary; skill instructions guide reporting and recommendations.
